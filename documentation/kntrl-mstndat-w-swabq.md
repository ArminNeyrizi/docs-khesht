# کنترل مستندات و سوابق

## هدف

اطمینان از استفاده از نسخه معتبر، ردیابی تصویب‌ها و نگهداری شواهد برای مدت لازم. GitBook رابط مستندسازی است و لزوماً مخزن مرجع همه سوابق پروژه، مالی، پرسنلی یا محدود محسوب نمی‌شود.

## طبقه‌بندی مستندات

| طبقه                   | نمونه                                       | کنترل معمول                             |
| ---------------------- | ------------------------------------------- | --------------------------------------- |
| خط‌مشی                 | خط‌مشی کیفیت یا حاکمیت                      | تصویب مدیریت و بازبینی                  |
| چارچوب/استاندارد داخلی | چارچوب IMS، استاندارد KPI                   | مالک، نسخه و وضعیت تصویب                |
| روش اجرایی             | بازبینی قرارداد، کنترل تغییر                | تصویب مالک فرایند                       |
| دستورکار/چک‌لیست       | بازرسی سایت، اختتام پروژه                   | تأیید فنی و کنترل بازنگری               |
| الگو/فرم               | ارزیابی ریسک، ثبت تصمیم                     | نسخه مادر کنترل‌شده                     |
| سابقه                  | پیشنهاد مصوب، گزارش بازرسی، صورت‌جلسه تحویل | یکپارچگی، دسترسی و نگهداری              |
| سند بیرونی             | قانون، مقرره، مشخصات مشتری                  | منبع، دامنه کاربرد، ویرایش و مسئول پایش |

## فراداده الزامی

هر سند کنترل‌شده باید شناسه، عنوان، هدف، مالک، تصویب‌کننده، تاریخ تصویب، نسخه، وضعیت، تاریخ اجرا در صورت کاربرد، دامنه، مخاطبان، اسناد مرتبط و سابقه تغییر را مشخص کند.

وضعیت‌ها: پیش‌نویس، در حال بازبینی، مصوب، جایگزین‌شده یا منسوخ. پیش‌نویس باید از دستورالعمل مصوب قابل تشخیص باشد.

## شناسه‌گذاری پیشنهادی

پیشوندهای پیشنهادی: IMS (نظام مدیریت یکپارچه)، GOV (حاکمیت)، PRC (فرایند/روش اجرایی)، QMS (کیفیت)، RSK (ریسک)، KPI (عملکرد)، FRM (فرم)، REC (سابقه)، AUD (ممیزی) و CAPA (اقدام اصلاحی). نمونه نمایشی: PRC-ENG-001، بازنگری ۰٫۱، وضعیت پیش‌نویس.

## گردش تصویب و بازنگری

1. مالک سند پیش‌نویس یا درخواست تغییر را تهیه می‌کند.
2. نقش‌های مرتبط مانند فنی، حقوقی، مالی، ایمنی یا امنیت اطلاعات در صورت نیاز بازبینی می‌کنند.
3. تصویب‌کننده مجاز تصویب یا بازگشت برای اصلاح را ثبت می‌کند.
4. نسخه معتبر به‌وضوح مشخص می‌شود.
5. در صورت لزوم کاربران مطلع یا آموزش داده می‌شوند.
6. نسخه جایگزین‌شده از استفاده عادی خارج می‌شود، اما برای ردیابی نگهداری می‌شود.
7. پس از تغییر مهم یا خطای تکرارشونده، اثربخشی بررسی می‌شود.

درخواست تغییر GitHub و GitBook می‌تواند بازبینی و تاریخچه نسخه را پشتیبانی کند؛ اما خشت باید مرجع مجاز تصویب هر طبقه سند را تعیین کند.

## نگهداری سوابق و دسترسی

برای هر نوع سابقه، مالک، سامانه منبع، طبقه‌بندی دسترسی، مدت نگهداری، مبنای قانونی یا قراردادی، نیاز پشتیبان‌گیری و روش امحا مشخص شود. مدت نگهداری باید با قوانین، قراردادها و نیازهای کسب‌وکار تطبیق داده شود.

اطلاعات شخصی، مالی، قراردادی و امنیتی محدود بماند. داده محرمانه پروژه، اطلاعات هویتی، اعتبارنامه یا نسخه نامحدود سوابق کنترل‌شده نباید در مخزن عمومی قرار گیرد.

## محرک‌های بازبینی

تغییر قانون یا قرارداد، تغییر مالک یا گردش کار، تغییر سامانه، یافته ممیزی، حادثه مهم، افت پایدار شاخص یا رسیدن موعد بازبینی باید موجب بررسی سند شود.
